## Deployment workflow and automatic-deployment investigation (2026-09-18, post-Phase-4.6)

**Confirmed manual workflow (unchanged, used for every Phase 4.x release this project has done):** `git add <exact files>` → `git commit` → `git push origin main` → `npx wrangler deploy` (from the repo root; reads `wrangler.jsonc`, builds `dist/codivio`/`dist/client` via the already-run `npm run build`, uploads changed assets, prints a `Current Version ID`) → live HTTP verification (status codes, security headers, byte-for-byte bundle diff against the local `dist/client` output).

**Observed automatic-deployment behavior (real, repeated, not yet fully explained):** across the Phase 4.4, 4.5, and 4.6 release checkpoints, `npx wrangler deployments list --json` shows **one or two additional deployments appearing after every manual `wrangler deploy`** — one roughly 7–12 seconds later, another roughly 4 minutes later — each a genuine, complete deployment (distinct `id`, `strategy:"percentage"`, 100% to one version), not a partial/duplicate artifact of a single CLI invocation. In every case before the Phase 4.6 scanner commit, this was invisible because the deployed content matched regardless of which deployment "won"; it became visible only when a manual deploy carried locally-uncommitted code that a rebuild-from-git would not include (see "vCard/WiFi/Scanner" release checkpoints above for the specific incident).

**Confirmed facts about the mechanism** (from `wrangler deployments list --json`, a read-only Wrangler command — no Cloudflare Dashboard access was used or is authorized):
- Every deployment record examined, including the unexplained ones, reports `"source": "wrangler"` and `"annotations": {"workers/triggered_by": "deployment"}` — identical to the deployments this session triggered directly and knowingly.
- No GitHub Actions workflow exists in this repository (`.github/` absent; no `.yml`/`.yaml` file anywhere outside `node_modules`).
- Neither `.githooks/pre-commit` nor `.githooks/pre-push` (the only two hooks that exist — there is no `post-commit`/`post-push` hook) contains any reference to `wrangler` or `deploy`; both only run `scripts/pre-commit-check.mjs`/`scripts/pre-push-check.mjs`, which do typecheck/lint/test/build/lockfile checks only.
- `package.json` has no `deploy` script and no CI/build-automation devDependency.
- `.wrangler/` (local Wrangler state, including `.wrangler/deploy/config.json`) is git-ignored and local-only — it cannot itself cause a *server-side* deployment, and nothing in it was found to reference an external trigger.
- `wrangler deployments list` cited above is capped at "the 10 most recent deployments" by the tool itself — the list's apparent start time (~09:30 that day) is this cap, not evidence bounding when the behavior began.

**Hypotheses considered — none confirmed:**
- *Cloudflare Git integration / "Builds" (a dashboard-configured feature that rebuilds and deploys on every push to the connected branch)* — remains the leading hypothesis based on the timing correlation with `git push`, but the `"source": "wrangler"` label on every record is not clearly consistent with it, and is not clearly inconsistent either — it is not known whether Cloudflare's deployment API tags Git-triggered deployments with a different `source` value or with the same one. Confirming or ruling this out requires the Cloudflare Dashboard's Settings → Builds page, which was not accessed (not authorized in any task so far).
- *A second local/external process independently invoking the `wrangler` CLI against this same account* — not ruled out; no evidence for or against was found on this machine within the scope of what was inspected.
- *An internal, undocumented two-phase behavior of a single `wrangler deploy` CLI invocation* — considered less likely, since each extra record is a distinct, complete, 100%-traffic deployment rather than a partial/staged one, but not independently disproven.

**Remaining unknowns:** `UNKNOWN — NOT VERIFIED` — the exact mechanism; whether it is safe to rely on, should be disabled, or should become the project's primary deploy path; whether it will reliably reproduce the same content as the local build every time, or could ever diverge in a way that ships something unintended.

**Recommended safe deployment workflow until the mechanism is confirmed:**
1. **Always commit and push the complete, intended change set before running `wrangler deploy`** — never deploy code that is not also committed and pushed. This session's Phase 4.6 incident (manually deploying uncommitted scanner code, which was then silently superseded by a same-content-as-git automatic redeploy minutes later) is exactly the failure mode this avoids.
2. **After every deploy (manual or automatic), always re-verify live**, not just trust the deploy command's own success output: check the live `index.html`'s referenced asset hashes match the current local build, confirm each referenced asset's `Content-Type` (not just HTTP status — a 200 can be this project's SPA fallback, not the real file), and byte-diff at least the main bundle against local `dist/client` output.
3. **Do not assume a single `wrangler deploy` is the last word** — as observed, a further automatic deployment can occur up to several minutes afterward; if time permits, re-check live state again a few minutes after deploying, especially before telling a stakeholder a release is confirmed live.
4. Treat any future confirmation of the actual mechanism (e.g., a deliberate, explicitly-authorized look at the Cloudflare Dashboard) as worth recording here as a follow-up to this entry.

## Deployment workflow and automatic-deployment investigation (2026-09-18/19, Phase 4.6 release)

During the Phase 4.6 release, deploying locally-uncommitted scanner code and then committing/pushing only a smaller subset (the security-header fix) revealed that **an automatic deployment occurs shortly after every `git push`** — confirmed by `npx wrangler deployments list --json` showing extra deployments (`"source": "wrangler"`, identical label to manually-triggered ones) appearing ~7–12 seconds and ~4 minutes after pushes, across multiple release checkpoints. **The exact mechanism remains `UNKNOWN — NOT VERIFIED`** — Cloudflare Git integration/Builds is the leading hypothesis based on push-timing correlation, but is not confirmed (the Cloudflare Dashboard was not accessed, per every task's explicit restriction). Ruled out by direct inspection: GitHub Actions (no `.github/` directory, no `.yml`/`.yaml` file anywhere outside `node_modules`), the project's own git hooks (`.githooks/pre-commit`/`pre-push` reference neither `wrangler` nor `deploy`), and any `deploy` npm script (none exists).

**Recommended safe workflow, followed successfully for the Phase 4.6 and 4.7 releases:**
1. Always commit and push the complete, intended change set **before** running `wrangler deploy` — never deploy code that isn't also committed and pushed.
2. Always re-verify live after any deploy: check the live `index.html`'s referenced asset hashes match the current build, confirm each asset's real `Content-Type` (a `200` can be this project's SPA fallback, not the real file), and byte-diff at least the main bundle against the local `dist/client` output.
3. Don't assume a single `wrangler deploy` is the last word — a further automatic deployment can occur up to several minutes afterward.

## GA4 Configuration Hardening + Generic Tool-Lifecycle Events (Phase 3.21)

**Implemented and tested — NOT YET committed, pushed, or deployed** (awaiting explicit authorization). GA4 itself was already implemented and live (Phase 3.16, `src/lib/analytics.ts`) — this task hardens its configuration and closes a real event-coverage gap; it is not a from-scratch GA4 build, and the task's own initial framing ("implement a minimal GA4 integration") was corrected against that reality during the inspection step it explicitly requested.

- **Measurement ID made configurable, never hardcoded**: `GA4_MEASUREMENT_ID` moved from a literal string (`"G-NFMYHQX593"`) to `import.meta.env.VITE_GA4_MEASUREMENT_ID` (new `src/vite-env.d.ts` for the ambient `ImportMetaEnv` type — this project had never used Vite env vars in code before; `.env.example` documents the new key).
