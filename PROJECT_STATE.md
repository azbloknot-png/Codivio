## Audit Logging status

**Implemented (Phase 2.6).** `worker/audit.ts#auditLog(env, event)` writes to the existing (now-extended) `audit_logs` table. Closed action vocabulary today: `AUTH_LOGIN_SUCCESS`, `AUTH_LOGIN_FAILURE`, `AUTH_LOGOUT`, `AUTH_BOOTSTRAP`, `AUTH_SESSION_EXPIRED`, `AUTHZ_DENIED` — extensible later (Pages/Tools/Users/Settings actions) without touching existing rows. Wired into every real current auth/RBAC event: login success/failure (including rate-limited and inactive-user cases), logout (only when a real session existed), bootstrap success/already-bootstrapped-denial, session expiry, and `authorize()`'s 403 path (both the general pipeline and `handleSession`'s inline check) — **plain 401s are deliberately not logged** (expected default for anonymous traffic, would be pure noise). Actor is always the real DB-resolved user or `null`, never anything from the request body/headers (test-verified against a forged `X-Role`/body). No secrets/passwords/hashes/tokens/raw cookies are ever written (test-verified across a full login+logout+denial cycle). IP is captured only from Cloudflare's edge-set `CF-Connecting-IP` header (never a client-spoofable one), and is `null` whenever that header is absent (e.g. everywhere in this local environment). **Failure policy: fail-open** — a failed audit write is logged to the Worker's own console and never blocks/alters the primary operation (test-verified: login still succeeds if the audit insert itself throws). No Admin UI or read endpoint for audit logs was built — none was needed to verify this checkpoint, and a public/UI read path is explicitly future work requiring `audit.view`.

## Settings status

**Implemented (Phase 2.7).** Foundation only — not the final Settings UI/system. `shared/settings.ts` is the single centralized, fail-closed registry (9 keys today across `general`/`system`/`google`/`advertising`/`affiliate`/`security`; 18 category names and 5 value types reserved for future use, not yet all populated) — both the Worker and the frontend import from it, no duplicated key lists. Server endpoints: `GET /api/settings/public` (no auth, `is_public=1` rows only), `GET /api/admin/settings` (`settings.view`), `PATCH /api/admin/settings` (`settings.manage`, one key at a time, validated against the registry — unknown keys and wrong-typed/oversized values are rejected with 400, never silently coerced). Per the existing Phase 2.5 matrix, only `super_admin` actually has `settings.manage` — `admin` can view but not edit, which the Admin UI now reflects (read-only rendering when the viewer lacks `settings.manage`, enforced for real server-side regardless of what the UI shows). Every successful or failed PATCH writes a `SETTING_UPDATED` audit event (failures logged too, with the rejection reason, never the attempted value if the key is unrecognized). True secrets (API keys, OAuth client secrets, SMTP passwords) are explicitly **not** stored here — this table only ever holds non-secret configuration and "is this integration configured" status flags; real secrets belong in Cloudflare Worker Secrets (see DECISIONS.md). Admin UI: `/admin/settings` (nested under the now-`Outlet`-based `/admin` route — Dashboard and Settings are siblings) renders General/Branding/Integrations/Security/System groups from real API data only — Branding shows an honest "Coming soon" (zero registered settings there yet), Integrations show "Not configured" status badges (never a fake "Connected"), nothing else is fabricated.

## Pages Management status

**Implemented (Phase 2.9).** Foundation only — not Blog CMS, not the full SEO system, not a visual page builder. The existing `pages` table (Phase 0) was extended in place (migration `0005_pages_management.sql`) rather than replaced: `description`, `meta_title`, `meta_description`, `canonical_url`, `is_indexable`, `created_by`, `updated_by` columns added. `shared/pages.ts` is the centralized, fail-closed validation registry (slug format/reserved-slug list, per-field length limits, status enum, canonical URL scheme check) — both Worker and frontend import from it, same pattern as `shared/rbac.ts`/`shared/settings.ts`. Server endpoints: `GET/POST /api/admin/pages` and `GET/PATCH/DELETE /api/admin/pages/:id` (all via `authorize()` — `pages.view` for reads, `pages.manage` for writes, both permissions already existed in the Phase 2.5 matrix, unchanged), plus an unauthenticated `GET /api/pages/:slug` that only ever returns a `status='published'` row (enforced in the SQL `WHERE`, not filtered after the fact) — a draft/archived page and a nonexistent slug both return the same generic 404. Mass-assignment protection is structural: create/update handlers only ever read the named allowed fields from the request body; `id`/`created_at`/`created_by`/`updated_by` always come from the server. A published page must be archived before it can be deleted (409 otherwise) — the safer default per CLAUDE.md §18, avoiding accidental hard-deletes of live/indexed content. Content-safety strategy is deliberately asymmetric: `title`/`description`/`metaTitle`/`metaDescription` reject raw `<`/`>` outright (defense in depth on short metadata fields with no legitimate reason to hold markup), while `content` is stored verbatim as plain text — its safety comes from the render side, not input filtering: the public route (`CmsPageRoute`/`CmsPageContent` in `src/App.tsx`) renders it via plain React text interpolation only, never `dangerouslySetInnerHTML` (verified by a permanent static test). Every mutation writes a real audit event (`PAGE_CREATED`/`PAGE_UPDATED`/`PAGE_PUBLISHED`/`PAGE_ARCHIVED`/`PAGE_DELETED`, added to `worker/audit.ts`'s closed vocabulary) with the real server-resolved actor, never a client-supplied one. Admin UI: `/admin/pages` (nested under `/admin`, sibling to Dashboard/Settings) — a real-data-only list ("No pages yet" when empty, never fabricated rows) with inline Publish/Unpublish/Archive/Delete actions and a shared create/edit form; a role with `pages.view` but not `pages.manage` sees the same list read-only (no role in today's matrix is actually in that state — every role with `pages.view` also has `pages.manage` — but the UI branch exists for correctness regardless of future matrix changes). Public rendering foundation: a top-level `/:slug` route (`CmsPageRoute`) fetches the public endpoint and renders title/description/content as plain text inside the existing `.legal-content`/`.page-intro` styling — React Router's static-route-ranking plus an explicit `RESERVED_PAGE_SLUGS` list in `shared/pages.ts` both independently prevent a page slug from ever shadowing `/admin`, `/api`, `/tools`, `/blog`, `/faq`, `/about`, `/contact`, `/privacy`, `/terms`, or `/cookies`.

## Security Headers status

**Implemented (Phase 2.11).** `worker/security-headers.ts#withSecurityHeaders` is applied once, at the single top-level `fetch()` in `worker/index.ts`, to every response the Worker returns (API and static-asset-forwarded alike): `Content-Security-Policy` (strict — `script-src 'self'`, `style-src 'self'`, no `unsafe-inline`/`unsafe-eval`, `frame-ancestors 'none'`, `object-src 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/microphone/geolocation/payment all denied), `X-Frame-Options: DENY` (legacy fallback), and `Strict-Transport-Security` (only added when the request actually arrived over HTTPS, mirroring the existing cookie `Secure`-flag pattern). The CSP was derived from actually inspecting the shipped build output (one same-origin script, one same-origin stylesheet, zero external hosts) — not copied from a template — and the one pre-existing inline `style={}` in the whole frontend was replaced with a CSS class specifically so `style-src` needs no exception. **This has been verified by static analysis of the actual build and by unit tests, not by a live deployed request** — see Known limitations.

## Known limitations / blockers

- Local `workerd` cannot boot on this machine (see Worker/Cloudflare status above). This also meant `npm test` itself was briefly broken (see below) — now fixed.
- Real D1 database/`database_id` requires Cloudflare account access not available here.
- `database/schema.sql` duplicates the migrations' content by design (a canonical current-state snapshot, not a single source of truth) — it had drifted out of sync after migration `0002` and was corrected this checkpoint (Phase 2.6) to also reflect `0002` and `0003`. Keep this in mind for every future migration: update `schema.sql` too, or it will drift again.
- No component-testing setup (`@testing-library/react`/jsdom) exists for React UI. Phase 2.4's Admin UI tests therefore combine real unit tests of extracted pure logic (`describeLoginError`, `resolveSessionState`) with structural/static source checks for the actual redirect/routing behavior — not a live-rendered/browser test. Adding jsdom/RTL would be the natural next step once React UI testing needs grow past what structural checks can responsibly cover.
- `PROJECT_PLAN.md` (an older planning doc) still describes a multi-package `apps/`/`packages/`/`worker-api` layout that predates and conflicts with the Modular Monolith decision — not yet reconciled.
- **`vitest.config.ts` must stay separate from `vite.config.ts`** — see `DECISIONS.md`. Merging them back will silently reintroduce the `workerd`-boot crash into every `npm test` run.
- A real timestamp-format bug (SQLite's `CURRENT_TIMESTAMP` vs JS `Date#toISOString()` not string-comparing correctly) was found and fixed in the login-lockout logic before it ever shipped — caught by testing the exact query against a real SQLite engine, not by code review alone. Worth remembering as a general D1 gotcha for future timestamp-comparison code.
- No DB-level `CHECK` constraint restricts `users.role` to the four known values.
