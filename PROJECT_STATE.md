## Audit Logging status

**Implemented (Phase 2.6).** `worker/audit.ts#auditLog(env, event)` writes to the existing (now-extended) `audit_logs` table. Closed action vocabulary today: `AUTH_LOGIN_SUCCESS`, `AUTH_LOGIN_FAILURE`, `AUTH_LOGOUT`, `AUTH_BOOTSTRAP`, `AUTH_SESSION_EXPIRED`, `AUTHZ_DENIED` — extensible later (Pages/Tools/Users/Settings actions) without touching existing rows. Wired into every real current auth/RBAC event: login success/failure (including rate-limited and inactive-user cases), logout (only when a real session existed), bootstrap success/already-bootstrapped-denial, session expiry, and `authorize()`'s 403 path (both the general pipeline and `handleSession`'s inline check) — **plain 401s are deliberately not logged** (expected default for anonymous traffic, would be pure noise). Actor is always the real DB-resolved user or `null`, never anything from the request body/headers (test-verified against a forged `X-Role`/body). No secrets/passwords/hashes/tokens/raw cookies are ever written (test-verified across a full login+logout+denial cycle). IP is captured only from Cloudflare's edge-set `CF-Connecting-IP` header (never a client-spoofable one), and is `null` whenever that header is absent (e.g. everywhere in this local environment). **Failure policy: fail-open** — a failed audit write is logged to the Worker's own console and never blocks/alters the primary operation (test-verified: login still succeeds if the audit insert itself throws). No Admin UI or read endpoint for audit logs was built — none was needed to verify this checkpoint, and a public/UI read path is explicitly future work requiring `audit.view`.

## Pages Management status

**Implemented (Phase 2.9).** Foundation only — not Blog CMS, not the full SEO system, not a visual page builder. The existing `pages` table (Phase 0) was extended in place (migration `0005_pages_management.sql`) rather than replaced: `description`, `meta_title`, `meta_description`, `canonical_url`, `is_indexable`, `created_by`, `updated_by` columns added. `shared/pages.ts` is the centralized, fail-closed validation registry (slug format/reserved-slug list, per-field length limits, status enum, canonical URL scheme check) — both Worker and frontend import from it, same pattern as `shared/rbac.ts`/`shared/settings.ts`. Server endpoints: `GET/POST /api/admin/pages` and `GET/PATCH/DELETE /api/admin/pages/:id` (all via `authorize()` — `pages.view` for reads, `pages.manage` for writes, both permissions already existed in the Phase 2.5 matrix, unchanged), plus an unauthenticated `GET /api/pages/:slug` that only ever returns a `status='published'` row (enforced in the SQL `WHERE`, not filtered after the fact) — a draft/archived page and a nonexistent slug both return the same generic 404. Mass-assignment protection is structural: create/update handlers only ever read the named allowed fields from the request body; `id`/`created_at`/`created_by`/`updated_by` always come from the server. A published page must be archived before it can be deleted (409 otherwise) — the safer default per CLAUDE.md §18, avoiding accidental hard-deletes of live/indexed content. Content-safety strategy is deliberately asymmetric: `title`/`description`/`metaTitle`/`metaDescription` reject raw `<`/`>` outright (defense in depth on short metadata fields with no legitimate reason to hold markup), while `content` is stored verbatim as plain text — its safety comes from the render side, not input filtering: the public route (`CmsPageRoute`/`CmsPageContent` in `src/App.tsx`) renders it via plain React text interpolation only, never `dangerouslySetInnerHTML` (verified by a permanent static test).
