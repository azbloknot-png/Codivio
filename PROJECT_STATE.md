## Audit Logging status

**Implemented (Phase 2.6).** `worker/audit.ts#auditLog(env, event)` writes to the existing (now-extended) `audit_logs` table. Closed action vocabulary today: `AUTH_LOGIN_SUCCESS`, `AUTH_LOGIN_FAILURE`, `AUTH_LOGOUT`, `AUTH_BOOTSTRAP`, `AUTH_SESSION_EXPIRED`, `AUTHZ_DENIED` — extensible later (Pages/Tools/Users/Settings actions) without touching existing rows. Wired into every real current auth/RBAC event: login success/failure (including rate-limited and inactive-user cases), logout (only when a real session existed), bootstrap success/already-bootstrapped-denial, session expiry, and `authorize()`'s 403 path (both the general pipeline and `handleSession`'s inline check) — **plain 401s are deliberately not logged** (expected default for anonymous traffic, would be pure noise). Actor is always the real DB-resolved user or `null`, never anything from the request body/headers (test-verified against a forged `X-Role`/body). No secrets/passwords/hashes/tokens/raw cookies are ever written (test-verified across a full login+logout+denial cycle). IP is captured only from Cloudflare's edge-set `CF-Connecting-IP` header (never a client-spoofable one), and is `null` whenever that header is absent (e.g. everywhere in this local environment). **Failure policy: fail-open** — a failed audit write is logged to the Worker's own console and never blocks/alters the primary operation (test-verified: login still succeeds if the audit insert itself throws). No Admin UI or read endpoint for audit logs was built — none was needed to verify this checkpoint, and a public/UI read path is explicitly future work requiring `audit.view`.

## Pages Management status

**Implemented (Phase 2.9).** Foundation only — not Blog CMS, not the full SEO system, not a visual page builder. The existing `pages` table (Phase 0) was extended in place (migration `0005_pages_management.sql`) rather than replaced: `description`, `meta_title`, `meta_description`, `canonical_url`, `is_indexable`, `created_by`, `updated_by` columns added. `shared/pages.ts` is the centralized, fail-closed validation registry (slug format/reserved-slug list, per-field length limits, status enum, canonical URL scheme check) — both Worker and frontend import from it, same pattern as `shared/rbac.ts`/`shared/settings.ts`. Server endpoints: `GET/POST /api/admin/pages` and `GET/PATCH/DELETE /api/admin/pages/:id` (all via `authorize()` — `pages.view` for reads, `pages.manage` for writes, both permissions already existed in the Phase 2.5 matrix, unchanged), plus an unauthenticated `GET /api/pages/:slug` that only ever returns a `status='published'` row (enforced in the SQL `WHERE`, not filtered after the fact) — a draft/archived page and a nonexistent slug both return the same generic 404. Mass-assignment protection is structural: create/update handlers only ever read the named allowed fields from the request body; `id`/`created_at`/`created_by`/`updated_by` always come from the server. A published page must be archived before it can be deleted (409 otherwise) — the safer default per CLAUDE.md §18, avoiding accidental hard-deletes of live/indexed content. Content-safety strategy is deliberately asymmetric: `title`/`description`/`metaTitle`/`metaDescription` reject raw `<`/`>` outright (defense in depth on short metadata fields with no legitimate reason to hold markup), while `content` is stored verbatim as plain text — its safety comes from the render side, not input filtering: the public route (`CmsPageRoute`/`CmsPageContent` in `src/App.tsx`) renders it via plain React text interpolation only, never `dangerouslySetInnerHTML` (verified by a permanent static test). Every mutation writes a real audit event (`PAGE_CREATED`/`PAGE_UPDATED`/`PAGE_PUBLISHED`/`PAGE_ARCHIVED`/`PAGE_DELETED`, added to `worker/audit.ts`'s closed vocabulary) with the real server-resolved actor, never a client-supplied one. Admin UI: `/admin/pages` (nested under `/admin`, sibling to Dashboard/Settings) — a real-data-only list ("No pages yet" when empty, never fabricated rows) with inline Publish/Unpublish/Archive/Delete actions and a shared create/edit form; a role with `pages.view` but not `pages.manage` sees the same list read-only (no role in today's matrix is actually in that state — every role with `pages.view` also has `pages.manage` — but the UI branch exists for correctness regardless of future matrix changes). Public rendering foundation: a top-level `/:slug` route (`CmsPageRoute`) fetches the public endpoint and renders title/description/content as plain text inside the existing `.legal-content`/`.page-intro` styling — React Router's static-route-ranking plus an explicit `RESERVED_PAGE_SLUGS` list in `shared/pages.ts` both independently prevent a page slug from ever shadowing `/admin`, `/api`, `/tools`, `/blog`, `/faq`, `/about`, `/contact`, `/privacy`, `/terms`, or `/cookies`.

## Security Headers status

**Implemented (Phase 2.11).** `worker/security-headers.ts#withSecurityHeaders` is applied once, at the single top-level `fetch()` in `worker/index.ts`, to every response the Worker returns (API and static-asset-forwarded alike): `Content-Security-Policy` (strict — `script-src 'self'`, `style-src 'self'`, no `unsafe-inline`/`unsafe-eval`, `frame-ancestors 'none'`, `object-src 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/microphone/geolocation/payment all denied), `X-Frame-Options: DENY` (legacy fallback), and `Strict-Transport-Security` (only added when the request actually arrived over HTTPS, mirroring the existing cookie `Secure`-flag pattern). The CSP was derived from actually inspecting the shipped build output (one same-origin script, one same-origin stylesheet, zero external hosts) — not copied from a template — and the one pre-existing inline `style={}` in the whole frontend was replaced with a CSS class specifically so `style-src` needs no exception. **Verified twice against a real deployed request**, not just statically: the first live check found that HTML/asset responses (as opposed to `/api/*` JSON) were missing all headers, because Cloudflare's Workers-with-Assets platform serves matching static assets directly from its edge cache without invoking the Worker's `fetch()` — fixed by adding `assets.run_worker_first: true` to `wrangler.jsonc` (`f9706f6`) and re-verified live: all 6 headers now present on `/`, `/tools`, `/admin`, `/admin/login`, and `/api/health` alike.

## Multilanguage system status (Phase 2.15)

**Implemented.** Application-wide i18n covering Azerbaijani (`az`, default), Turkish (`tr`), and English (`en`). No worker/D1 schema/migration/auth/RBAC/security-header file was touched, except one minimal, explicitly-permitted validation addition (see below).

- **Architecture:** `shared/i18n/{languages,types,az,tr,en,index}.ts` — a framework-agnostic module (same pattern as `shared/rbac.ts`/`shared/settings.ts`), importable by both the Worker and the frontend. `Translations` is a nested-object TypeScript interface (not flat `"a.b.c"` string keys), so a missing/misspelled key across any of the 3 dictionaries is a compile error, not a silent runtime fallback — verified by `tsc` compiling clean for all three. A thin frontend-only layer, `src/i18n/{LanguageContext,LanguageSwitcher}.tsx`, provides a React context/hook (`useLanguage()`) and the reusable `<LanguageSwitcher />` control. No component contains a scattered `language === "xx"` branch anywhere (test-enforced, see Testing status) — every string comes from the current language's `Translations` object.
- **Persistence — two layers, not conflicting sources of truth:** (1) the pre-existing `general.default_language` D1 Setting (Phase 2.7, public, read via the already-existing `GET /api/settings/public` — no new endpoint) is the site-wide default for a visitor who has never chosen a language; editing it still goes through the exact same `PATCH /api/admin/settings` / `settings.manage` RBAC gate as any other setting. (2) `localStorage` (`codivio_language`) holds a given browser's own override, set the moment anyone uses the switcher (public header or Admin) — it is checked first and, once set, always wins over the site default on that device. The hardcoded fallback `DEFAULT_LANGUAGE = "az"` is applied synchronously as React's initial state, so first paint is never blocked on a network request; the site-default fetch only runs, and only ever upgrades state, when no local override exists yet.
- **Backend-adjacent change (minimal, explicitly permitted):** `shared/settings.ts#validateSettingValue` now rejects any `general.default_language` value outside `LANGUAGES` (`az`/`tr`/`en`) — fail-closed validation consistent with every other typed setting, no schema/migration change. The already-live production value (`"en"`, seeded at Phase 2.7) was deliberately left as-is — not edited/migrated, since mutating data in already-applied production migrations is unsafe drift; a `super_admin` can change it via Settings → Language like any other setting.
- **Wording fixes (the actual point of this phase, not just plumbing):** the four awkward "Whether X has been configured/enabled" settings descriptions were replaced with real yes/no questions in all 3 languages (e.g. EN: "Is Google Analytics configured?", AZ: "Google Analytics konfiqurasiya olunub?", TR: "Google Analytics yapılandırıldı mı?" — and the same pattern for Search Console/AdSense/the affiliate program). All 9 real setting keys have a translated `settingLabel` entry — none fall back to `shared/settings.ts`'s raw internal `description` field in the UI (verified by grep: the raw "Whether…" strings only exist as backend registry metadata now, never rendered). Status vocabulary (Coming soon/Not configured/Disabled/Configured/Enabled/etc.) is now centralized and consistent across every Admin surface.
- **Coverage:** Admin nav (all 16 modules), login screen, dashboard placeholder cards, all 15 Settings tabs (14 original + new "Language" tab, `general.default_language` moved off the General tab onto its own), the 12 `AdminComingSoonPage` placeholders (refactored from per-route literal props to a single `moduleKey` prop resolved against the dictionaries — eliminates the prior literal-string duplication across `App.tsx`), Pages/Tools admin list+editor chrome (headings/buttons/empty states/Yes-No — **not** their form field labels, a documented scope boundary, see Known limitations), and the public Homepage's header/footer/hero/all 5 section headings. **Not translated** (explicit, documented scope boundary — "make focused corrections, don't redesign everything"): the 34-tool registry names/descriptions, category-filter pills, FAQ/About/Contact/legal page bodies, Blog post content, and Pages/Tools editor form field labels.
- **Responsive:** the switcher (`.language-switcher` in `src/styles.css`) has no fixed pixel width (`min-width:0; max-width:100%`, flex-shrink applied in its parent flex rows), so longer AZ/TR option text cannot force horizontal overflow in the header, Admin header, or Settings tab — test-enforced (see Testing status).
