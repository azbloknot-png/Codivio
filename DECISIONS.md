# CODIVIO — DECISIONS LOG

Short, approved architectural/product decisions only. Full rules live in `CLAUDE.md` — this file records *what was decided and why*, not the rule text itself. Newest-relevant decisions grouped by area; no strict chronology required.

## Architecture

- **Modular monolith first.** One deployable Cloudflare Workers app with internal module boundaries; do not split into separate services/repos. *Reason: matches team size and current scale; avoids premature distributed-systems overhead.*
- **Selective microservices only when justified.** Splitting out a service later requires real load/ownership evidence, not speculation. *Reason: keep the option open without paying its cost now.*
- **Cloudflare Workers + D1 direction.** Confirmed via `wrangler.jsonc` + `worker/index.ts` (Phase 2.2). *Reason: aligns with the free/low-cost infrastructure principle and existing Cloudflare Pages/Assets setup.*
- **SQLite-compatible relational design where applicable.** `database/schema.sql` targets D1's SQLite dialect (e.g. `AUTOINCREMENT`, `PRAGMA foreign_keys`). *Reason: D1 is the chosen database; no ORM/abstraction layer added.*

## Homepage / Tool Registry

- **Homepage shows exactly 12 selected tools; all registered tools/routes remain preserved.** `HOMEPAGE_FEATURED_TOOLS` is a filtered view (`tools.filter(t => t.featured)`), never a copy or deletion of the registry. *Reason: curated homepage UX without losing the full catalog or breaking `/tools/:slug` routes.*
- **Popular/QR/PDF tool groups are independently managed.** Separate `popular`/`qr`/`pdf` boolean flags, each its own derived list — not aliases of `featured`. *Reason: lets a future Admin Panel curate each homepage section independently, with no code change. Status: implemented (2026-09, Phase 2 UI work).*

## Admin / Security

- **Admin is intended to become the central no-code/low-code management center**, not just a read-only dashboard — covering homepage tool ordering, Popular/QR/PDF/Other curation, tool active/inactive, content, SEO, ads, users, and settings. *Reason: stated product goal for Phase 2+; drives §7/§14 of CLAUDE.md and the `codivio-admin` skill's checkpoint list.*
- **Security-first admin architecture.** Auth/RBAC/session/audit-log work follows CLAUDE.md §19 Change Control (inspect → risk → smallest safe change → test → security review → diff review → report), not the lighter default Testing Gate. *Reason: Admin is the highest-risk surface built so far.*
- **IP limits are abuse protection, not permanent identity.** Rate-limiting by IP (e.g. login attempts) must not be treated as a durable user/device identifier. *Reason: avoid conflating anti-abuse tooling with identity/authorization logic.*

## Monetization (future, not yet built)

- **Future Free/Pro/Business entitlement architecture** is anticipated but not implemented. *Reason: keep today's data model from blocking it later, without building it prematurely.*
- **Affiliate services and Codivio-owned premium services remain logically separate.** Even in future schema/architecture, these must not be merged into one undifferentiated "monetization" concept. *Reason: different risk, accounting, and disclosure requirements.*
- **Social media integrations use official APIs/webhooks where available**, not scraping or unofficial endpoints. *Reason: reliability and ToS compliance for any future share/post features.*

## Authentication (Phase 2.3)

- **Password hashing via PBKDF2-SHA256 (Web Crypto), not a custom algorithm.** 100,000 iterations, random 16-byte salt, self-describing stored format. *Reason: the Workers runtime has no native bcrypt/argon2; PBKDF2 via the standard Web Crypto API is a recognized, non-invented algorithm that needs no new dependency.*
- **Session tokens are stored as a SHA-256 hash, never the raw value, in D1.** The raw token exists only in the `HttpOnly` cookie. *Reason: a database read alone then can't be replayed as a valid session — defense in depth beyond just "the cookie is HttpOnly."*
- **Failed-login lockout is keyed by the attempted email, not by IP; no IP address is stored.** *Reason: direct application of the existing "IP limits are abuse protection, not permanent identity" decision — this is the minimum mechanism that still protects a specific account from credential guessing.*
- **`vitest.config.ts` is kept separate from `vite.config.ts`.** *Reason: `vite.config.ts` conditionally loads `@cloudflare/vite-plugin`, which tries to boot a Miniflare/`workerd` runtime during `vitest run` (Vitest sets `NODE_ENV=test`, not `"development"`) — this crashes on this machine and would otherwise break every test run, not just Worker-related ones. Status: implemented 2026-09 (Phase 2.3); do not merge these configs back together without addressing the underlying plugin/test interaction first.*

## Admin UI (Phase 2.4)

- **Admin code lives in its own `src/admin/` module, not folded into `App.tsx`.** *Reason: `App.tsx` was already ~1,700 lines before Admin work started; Admin is a genuinely separate, growing concern (2.5 RBAC, 2.9 Pages, 2.10 Tools all extend it) and deserves its own file from the start rather than compounding the existing monolith.*
- **Admin auth state is per-route local hooks (`useSession`), not a global context/store.** *Reason: explicit user instruction to keep it simple; the server session (`GET /api/auth/session`) is the only source of truth regardless, so a shared client store would only cache what's re-checked on each protected route anyway. Revisit only if real duplication/UX cost is observed.*
- **The Admin login page reuses the existing `Code2` icon brand mark (same as the public site header/footer), not the unused `public/assets/branding/codivio-logo.png` file.** *Reason: the real logo PNG has never been wired into any page yet; introducing it for the first time only in Admin would create a visible brand-mark inconsistency between public and admin. Revisit together, sitewide, if/when the real logo is ever adopted.*

## RBAC (Phase 2.5)

- **The role/permission matrix is defined once, in `shared/rbac.ts`, imported by both the Worker and the frontend.** *Reason: explicit instruction to avoid scattered `role === "..."` checks and matrix duplication; a plain, framework-free TS module is importable from both Vite build environments without any bridging code.*
- **The initial permission matrix (super_admin/admin/editor/analyst) was reviewed and implemented exactly as specified — no security or architectural problem was found in it.** Every role's permissions are a coherent subset within the hierarchy (analyst ⊆ editor's base access; admin ⊇ editor's content permissions plus read-only users/settings/analytics/audit visibility; super_admin ⊇ everything), and no permission is granted automatically just because a role exists. *Status: implemented 2026-09 (Phase 2.5) as given; if a future checkpoint wants to change it, that is a new decision to record here, not a silent edit.*
- **A DB-level `CHECK` constraint on `users.role` is deliberately deferred**, relying on `shared/rbac.ts#isValidRole`'s fail-closed application-layer check instead. *Reason: SQLite/D1 cannot add a `CHECK` to an existing column without rebuilding the table (a risky migration, and unverifiable here without live D1 access) for a case no current code path can trigger (only bootstrap creates users, always with `role = "super_admin"`). Revisit once real role-editing exists.*
- **`worker/rbac.ts` depends on `worker/auth.ts` one-directionally, never the reverse.** `auth.ts`'s own `handleSession` checks permissions inline rather than calling `rbac.ts#authorize()`. *Reason: avoids a circular import; `auth.ts` is the lower-level "who is this" primitive, `rbac.ts` the higher-level "are they allowed" orchestration built on top of it. Future protected endpoints (Phase 2.9+) should import `authorize()` from `rbac.ts`.*
- **Admin nav items are hidden entirely if the role lacks the underlying permission, and shown as "Soon" only if the role has the permission but the feature isn't built yet.** *Reason: don't advertise a feature a role will never be allowed to use; do tease one it will eventually get. This is UI convenience only, not a security control.*

## Audit Logging (Phase 2.6)

- **Audit logging is fail-open, uniformly, for every event type.** A failed write is reported via `console.error` (visible in Worker logs) but never blocks, delays, or changes the outcome of the operation being audited. *Reason: audit logging is a detective control, not a preventive one — its own unavailability (a transient D1 hiccup, or right now, no real D1 being provisioned at all) must not become an authentication/authorization outage. One consistent policy, not decided per call site.*
- **The existing Phase 0 `audit_logs` table was extended, not replaced.** Migration `0003` adds `actor_email`/`result`/`ip_address`/`user_agent` columns and indexes to the table already defined in migration `0001`; no new table was created. *Reason: the original design (`user_id`, `action`, `entity_type`/`entity_id`, `metadata_json`, `created_at`) already covered most of what was needed — inspected first, extended only where genuinely missing.*
- **Failed-login audit entries never reference a real `user_id`, even when the email matches an existing account** — only `actor_email` is stored for failures. *Reason: avoids conflating "this account was probed" with "this account acted"; keeps the failure path's data shape identical regardless of whether the email exists, which also avoids a timing/existence side-channel in the logging path itself.*
- **IP address is captured only from Cloudflare's edge-set `CF-Connecting-IP` header, never a client-suppliable one like `X-Forwarded-For`, and is left `null` when absent** (which is always, in this local environment). *Reason: a spoofable IP field would be worse than no IP field for an audit trail; the mechanism's trustworthiness is a documented Cloudflare platform guarantee, not something this project can verify pre-deployment.*
- **Plain 401 (unauthenticated) requests are not audited; only authenticated-but-denied (403) events are.** *Reason: anonymous 401s are the expected default for routine traffic and would grow the log unboundedly with no security signal; a real account being denied a specific permission is the actionable event.*
- **`database/schema.sql` is a maintained canonical snapshot, not a one-time copy of migration `0001`.** Every future migration must update it too. *Reason: it had silently drifted after migration `0002` (Phase 2.3) went in without a matching schema.sql update; caught and corrected in Phase 2.6. Documented here so it isn't lost as a one-off fix and forgotten again.*

## Settings Foundation (Phase 2.7)

- **One generic `settings` table (key/value/value_type/category/is_public/description/updated_at/updated_by), not a table per future integration category.** *Reason: Google/Social/AdSense/Affiliate/etc. don't exist yet; a single flexible table with a centralized, code-level registry (`shared/settings.ts`) lets each be added later as new registry entries + seed rows, never a schema redesign.*
- **True secrets never live in this table.** API keys, OAuth client secrets, SMTP passwords, and similar belong in Cloudflare Worker Secrets. This table only stores non-secret configuration and "is this integration configured" status flags. *Reason: explicit requirement — D1 rows are not an appropriate place for high-value credentials Cloudflare already has a proper mechanism for.*
- **Unregistered setting keys are rejected (400), not silently created.** `shared/settings.ts`'s registry is the single fail-closed allowlist for both read-shaping and write validation. *Reason: prevents arbitrary key/value injection into an otherwise-flexible table; every new setting must be a deliberate code change (registry entry + migration seed row), never an ad-hoc runtime key.*
- **PATCH /api/admin/settings updates exactly one key per call, not a batch.** *Reason: avoids partial-apply/transaction complexity for a foundation this small; a batch endpoint can be added later if a real multi-field settings form needs it.*
- **A setting's `isPublic` (read exposure) and `isSensitive` (audit-metadata redaction) are independent flags.** A setting can be private without being sensitive (e.g. `google.analytics_configured`) or, in principle, public and still audited without its value (none currently are). *Reason: conflating "who can read it" with "should its value appear in logs" would have under- or over-protected one of the two cases.*
- **"Configured" status flags for not-yet-built integrations (Google/AdSense/Affiliate) are rendered read-only in the Admin UI, even for a role with `settings.manage`.** *Reason: no real integration flow exists yet to legitimately set them true; making them manually toggleable now would let an admin create a fake "Configured" status with nothing behind it, which is exactly what CLAUDE.md/this checkpoint prohibit. The underlying PATCH endpoint doesn't special-case this — it's a UI-only restraint until Phase 2.9+ builds the real integration flow that should set these server-side.*

## Pages Management (Phase 2.9)

- **The existing (Phase 0) `pages` table was extended in place, not replaced or duplicated.** It already had the right shape (id/slug/title/content/status/timestamps) for a CMS-style admin page; migration `0005` added `description`/`meta_title`/`meta_description`/`canonical_url`/`is_indexable`/`created_by`/`updated_by`. *Reason: matches the project's own "inspect first" convention (CLAUDE.md §1) rather than assuming a fresh table was needed.*
- **The existing (still unused) `seo_settings` table was deliberately NOT wired into Pages Management.** The four scalar SEO fields (`meta_title`/`meta_description`/`canonical_url`/`is_indexable`) were added directly to `pages` instead. *Reason: `seo_settings` models richer per-page SEO (Open Graph, `schema_json`, granular `robots` directives) intended for the Phase 3 SEO system; wiring it in now would require multi-table transactional writes for a foundation checkpoint that only needs four scalars. Revisit consolidation when Phase 3 SEO work begins.*
- **No DB-level `CHECK` constraint on `pages.status`**, relying on `shared/pages.ts#isValidPageStatus`'s fail-closed application-layer check instead. *Reason: identical to the existing `users.role` deferral — SQLite/D1 cannot add a `CHECK` to an existing column without a full table rebuild.*
- **Content-safety is asymmetric by field, not a blanket filter.** `title`/`description`/`metaTitle`/`metaDescription` reject raw `<`/`>` outright; `content` is stored verbatim with no character filtering. *Reason: the short metadata fields have no legitimate reason to hold markup, so rejecting it is pure upside; `content` is real body text that might legitimately need to quote or discuss markup, and its actual safety boundary is the render side (plain React text interpolation, never `dangerouslySetInnerHTML`) — filtering it at write time would be either redundant with that boundary or actively harmful (blocking a page from documenting a `<script>` tag as an example).*
- **A published page must be archived before it can be deleted** (`DELETE` returns 409 otherwise). *Reason: CLAUDE.md §18's "prefer safe behavior" — avoids an accidental hard-delete of live, possibly-indexed content; draft/archived pages can be deleted directly since they were never public.*
- **The public page endpoint (`GET /api/pages/:slug`) enforces `status = 'published'` inside the SQL `WHERE` clause itself, not as a post-query filter**, and returns the same generic 404 for both a missing slug and a real draft/archived one. *Reason: makes it structurally impossible for a future code change to accidentally leak a non-published page, and avoids a slug-existence side channel.*
- **A public page's slug can never be one of the existing top-level static routes** (`admin`/`api`/`tools`/`blog`/`faq`/`about`/`contact`/`privacy`/`terms`/`cookies`), enforced by an explicit `RESERVED_PAGE_SLUGS` allowlist check in `shared/pages.ts`, independent of React Router's own static-beats-dynamic route ranking. *Reason: defense in depth — don't rely solely on router behavior for a security-relevant routing guarantee; keep the reserved list in sync with `src/App.tsx`'s route table by hand.*

## Tools Management (Phase 2.10)

- **The existing (Phase 0) `tools`/`categories` tables were extended and seeded in place, not replaced or duplicated.** They already had nearly the right shape (slug UNIQUE, name, description, component, status, featured, sort_order, category_id -> categories) but had never been seeded — the frontend has always used its own static array. *Reason: matches the project's "inspect first" convention; the schema was already 80% of what was needed.*
- **Pre-existing column names (`featured`, `status`, `component`, `sort_order`) were kept as-is, not renamed to match the newer `is_`-prefixed convention** used by `pages.is_indexable`/`settings.is_public`. Only genuinely new columns (`is_popular`) adopted the newer style. *Reason: renaming an existing column requires a full SQLite table rebuild for no functional benefit; a small naming inconsistency between an old and new column is cheaper than that migration risk.*
- **The static tool registry in `src/App.tsx` remains the live source for the public site (Homepage, `/tools`, `/tools/:slug`) this phase — the new `tools`/`categories` D1 tables are an Admin-managed configuration surface with no public consumer yet.** *Reason: CLAUDE.md §10/§22's own escape hatch — wiring full public dynamic integration in the same checkpoint as the DB+API+RBAC+validation+audit+UI+security work would be unnecessary architectural risk for a "foundation" checkpoint; the two data sources cannot conflict because only one is ever actually read by public code paths. The remaining integration (point the public site at `GET`-style tool data instead of the static array) is explicit, documented future work, not assumed in progress.*
- **No public `GET /api/tools` endpoint was built.** *Reason: nothing in this checkpoint would consume it (see above) — building unused API surface violates CLAUDE.md §2's "no unrelated functionality." Add it in the same future checkpoint that actually wires the public site to the database.*
- **`TOOL_CATEGORIES` in `shared/tools.ts` is deliberately broader (includes `video`/`gif`/`ai`/`utilities`) than what the `categories` table currently holds (only `qr`/`pdf`/`image`/`other` are seeded).** A category is only actually usable once a real `categories` row exists for it — `worker/tools.ts` looks it up and fails closed (400) rather than auto-creating one. *Reason: documents the intended growth path (CLAUDE.md §4/§11's future tool categories) without prematurely creating unused category rows or over-complicating validation with a live DB round-trip inside the framework-agnostic `shared/` module.*
- **Icons are a controlled string-identifier allowlist (`ICON_NAMES`), never raw HTML/SVG/markup from a database value.** *Reason: explicit requirement — an icon column that accepted arbitrary markup would be a stored-XSS/arbitrary-HTML vector the moment anything renders it; a closed identifier list mirrors the same fail-closed pattern already used for roles/permissions/settings-categories/page-statuses.*
- **Deleting an active tool is blocked (409) until it is deactivated first** — the same safety pattern as Phase 2.9's "archive before delete" for pages. *Reason: CLAUDE.md §24 — a tool may be referenced by the homepage, routes, or future analytics/SEO/affiliate configuration; deactivation is the safe default lifecycle action, hard-delete is for already-inactive tools only.*

## Admin Security + Final Tests (Phase 2.11)

- **A single, uniform security-headers baseline is applied at one point** — `worker/index.ts`'s top-level `fetch()` wraps every response (both `/api/*` handlers and whatever `env.ASSETS.fetch()` returns for the SPA) via `worker/security-headers.ts#withSecurityHeaders`, rather than adding headers per-handler or via a separate `_headers` file. *Reason: one place, impossible to forget on a new route; verified safe by actually inspecting the built `index.html`/bundle (one same-origin script, one same-origin stylesheet, zero external hosts) before writing the CSP, not copied from a generic template.*
- **The Content-Security-Policy is strict now (`script-src 'self'`, `style-src 'self'`, no `unsafe-inline`/`unsafe-eval`) and should only ever be *loosened*, directive by directive, when a real integration genuinely needs it** (e.g. GA4's script host when Phase 3 adds it) — never widened speculatively ahead of that need. *Reason: matches CLAUDE.md §9/§10's "no arbitrary remote scripts, document why each external script exists" — the policy itself should enforce that discipline going forward, not just describe it.*
- **The one pre-existing inline `style={{ whiteSpace: "pre-wrap" }}` (the public CMS page body, Phase 2.9) was replaced with a CSS class (`.cms-page-content`)** specifically so `style-src` could stay `'self'` with no `'unsafe-inline'` exception. *Reason: a one-line, zero-risk change that measurably improves the CSP's strength — cheaper than carrying a permanent policy exception for a single call site.*
- **`img-src` allows `data:`** even though nothing uses it yet. *Reason: a client-rendered QR code preview (a very likely near-term Phase 4 need) would naturally want a `data:` image URI, and a `data:` image poses no script-execution risk — a deliberate, narrow, justified exception, not a general loosening.*
- **No CSRF token mechanism was added.** The existing `SameSite=Strict` + `HttpOnly` + `Secure` session cookie (Phase 2.3), combined with this being a same-origin architecture with no cross-origin embedding, already blocks the cookie from being sent on any cross-site request — including top-level navigations, which `SameSite=Lax` would still allow. *Reason: `SameSite=Strict` is already the strictest available setting; adding a token mechanism on top would be pure complexity with no additional protection for this architecture. Revisit only if a legitimate cross-origin flow (e.g. an OAuth callback) is ever introduced, since `Strict` cookies do not survive that redirect chain either.*
- **PBKDF2 iteration count (100,000) was reviewed, not changed.** Current OWASP guidance (2023) recommends 600,000 for PBKDF2-HMAC-SHA256, well above today's value — but Cloudflare Workers has a hard per-request CPU-time budget (as low as 10ms on the Free plan) that this environment cannot empirically measure locally (the standing `workerd`-on-Windows limitation). *Reason: raising a security-critical, performance-sensitive parameter without being able to verify it doesn't blow the platform's CPU budget would trade a documented, low-severity gap for an unverified, potentially request-failing one. The stored-hash format (`pbkdf2$<iterations>$<salt>$<hash>`) already self-describes its iteration count, so this can be raised later with zero migration cost and zero impact on existing hashes — recorded as a deferred, environment-gated item, not silently left alone.*
- **Deactivation-mid-session was verified, not assumed.** `resolveAuthenticatedUser`'s session/user JOIN already re-reads the live `users.status` on every request (not just at login), so deactivating a user immediately invalidates their still-unexpired session on their very next request. This existing behavior had no direct test until this checkpoint — one was added (`tests/rbac.test.ts`) rather than left as an inspected-but-unverified claim.

## Admin UI + Homepage Redesign (Phase 2.13)

- **`NAV_ITEMS`' `permission` field is now optional; an item without one is visible to any role that reached the Admin shell.** *Reason: 9 of the 16 requested Admin modules (Blog/SEO/Search Console/Advertising/Affiliate/Monetization/Social/Reports/System Health) have no backend or data to protect yet — inventing a permission in `shared/rbac.ts` for a page that shows nothing but a "Coming soon" list would be RBAC theater, not a real security boundary, and would have required touching the RBAC matrix for a purely cosmetic reason. The shell itself is already gated by `admin.access`.*
- **A single shared `AdminComingSoonPage` component, not one bespoke page per module**, represents every not-yet-built Admin module — 12 placeholder routes in total (the 9 permission-less modules above, plus Users/CRM, Analytics, and Audit Log, which have a real permission but no page built yet). *Reason: keeps every placeholder visually consistent and cheap to add/maintain; each just passes a title/description/category-chip list. None fabricate data, charts, or interactive controls.*
- **Tools Management's editor was NOT extended with the requested future fields** (Related tools, Usage, Errors, Performance, Monetization/Ad/Affiliate eligibility, Policy status). *Reason: none of these have a backing database column; an input field that silently saves nothing would be worse than no field at all. Extend the editor only alongside the migration that adds real columns for them.*
- **The official logo PNG (`public/assets/branding/codivio-logo.png`) is used unmodified; its square/dark-background presentation is handled entirely in CSS** (`.brand-logo{border-radius:10px;object-fit:cover}`), never by cropping/editing the source file. *Reason: the only available asset is a square, dark-background app-icon-style lockup, not a horizontal transparent header logo — clipping it into a rounded badge via CSS (a purely presentational, reversible transform) satisfies "use the official logo" and "do not alter the logo artwork itself" simultaneously.*
- **The new "Image & Other Tools" homepage slider is derived from the existing `category` field, not a new boolean flag** (unlike Popular/QR/PDF, which use dedicated flags). *Reason: every Image Tools and Other Tools registry entry belongs on this one shared section — there is no curation split to express with a separate flag, so adding one would be an unused, always-true field for 14 tools.*
- **The Admin Settings category-tab UI uses a simplified ARIA tabs pattern** (`role`/`aria-selected` present, no roving tabindex/arrow-key navigation). *Reason: this project has no component-testing setup to verify complex keyboard interaction live; native button Tab/Enter semantics already make every tab reachable and operable. Revisit if full APG tabs compliance becomes a real requirement.*

## Production Deployment (2026-09-13)

- **`assets.run_worker_first: true` was added to `wrangler.jsonc`.** *Reason: discovered live, not locally — Cloudflare's Workers-with-Assets platform serves a matching static asset directly from its edge cache without invoking the Worker's `fetch()` unless this is set, which meant `worker/security-headers.ts`'s headers never reached real HTML page responses (only `/api/*` had them). This is a documented, deliberate cost (every static asset request now runs through the Worker first, a small added latency) accepted specifically to make the security-headers guarantee actually true in production, not just in the code.*
- **`MAX_FAILED_ATTEMPTS` was raised from 5 to 25 (5×) for normal admin login use, with the same 15-minute rolling window and rate-limit mechanism kept unchanged.** *Reason: explicit user request after live use showed 5 was too easy to hit during normal admin work; still bounded, still fails closed above the threshold — not a removal of brute-force protection, a recalibration of it.*
- **A one-off production password reset used a local, ephemeral, uncommitted script that replicates `hashPassword()`'s exact algorithm, rather than any change to the application.** *Reason: needed to apply a real PBKDF2-SHA256 hash directly to one row in production D1 without inventing a new admin-facing "reset password" feature under time pressure; the script was deleted immediately after use and never committed. If password reset becomes a recurring need, it should become a real, tested Admin feature — not repeat this one-off pattern.*

## Process

- **Real statistics only; never fake/random production statistics.** Every usage/traffic/revenue number shown anywhere must come from real event/database data once that infrastructure exists. *Reason: explicit trust requirement — see CLAUDE.md §2 and §23.*
- **20% milestone requires a comprehensive audit and PASS before advancing.** Enforced via the `codivio-test-gate` skill. *Reason: prevent silent drift across phase boundaries.*
- **Testing philosophy: one appropriate test per topic; add another only when failure/uncertainty requires it.** *Reason: avoid redundant, token-costly re-testing of unrelated or already-verified areas.*
- **No commit/push before required tests/checkpoint approval**, and never without the user's explicit go-ahead regardless. *Reason: CLAUDE.md §18/§19; the user controls when work lands in Git history.*
